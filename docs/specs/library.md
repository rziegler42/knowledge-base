# Library

Status: Draft

This specifies the library, the whole collection: where its data lives, how one host serves it to the owner's machines, how it is
set up, moved, backed up and shared, and how it is kept healthy. It belongs to the design in `knowledge-base.md` and
builds on the book (`book.md`) and the shelf (`shelf.md`). **Nothing here is final.** The spec stays `Draft` until the owner
approves it, and any statement can be reopened. Each statement carries one of three marks:

- **[agreed]** The owner said it. It is the working position and it can still change.
- **[proposed]** The assistant's suggestion. The owner has not decided it.
- **[idea]** Exploratory. It is recorded so it is not lost, and it is not a requirement.

Much of this spec was split out of `knowledge-base.md`, and those statements keep their marks. The rest was added in the
conversation that followed.

## Scope

The library is the collection of shelves, books, cards, themes and, if built, the weave, together with the places where they are
stored and the host that serves them. This spec covers the four places that hold the project's code and data, the library id, the
host and client split, credentials and their rotation, network access, setup, relocation and the guard against
writing to an unmounted drive, backup, format versions and integrity, a library report with a growth forecast, a doctor
command, and later ideas about more than one library. It does not cover what a book, shelf, card or theme is, how the
pipeline runs, or the models; they have their own specs.

## Non-goals

- **[agreed]** Tracking the library in git. Only the engine (code, specs and documents) is ever committed, and data never is. Backup
  and history are the owner's to arrange.
- **[agreed]** Executing anything the library holds. A repository, script or document in the library is data and is never built or
  run.
- **[proposed]** Serving the library over the open internet. The host is for the owner's local network, and anything wider is the
  owner's own arrangement, such as a private network, and not part of this project.
- **[proposed]** Roles and fine-grained access control. There is the owner and there are guests (`shelf.md`).

## Assumptions and constraints

- The workbench's `knowledge-tools` spec reserves this module, proposes the capability name `knowledge-base`, and fixes its
  boundaries: library content is reference data and untrusted as instruction, a tracked document cites it by source URL, retrieval
  date and content hash and never by path, and an agent may run only reads that change nothing and send nothing out. Two exceptions,
  allowed by the owner on 2026-11-10 and 2026-11-14 and stated in full in `knowledge-base.md` (Assumptions and constraints): the helper arguments
  `problem-search` and `theme-walk` send the sub-problems or questions an agent wrote to the embedding model of the `card-embed` task, on the owner's server
  (on the owner's network, over plain HTTP), and to nothing else.
- The workbench decision `2026-10-20-fixed-store-location` explains why a store's location must not be changeable by an option, an
  environment variable or a committed file. The same reasoning is applied to addresses, tokens and the model registry.
- The workbench has no MCP layer, and one was deferred (decision `2026-10-21-module-code-lives-in-modules`). A module's interface
  is a pinned helper command, and permission rules match commands.
- The workbench's path rules refuse symlinks, so a mount point is handled deliberately.
- Adding a dependency, such as a vector index or a local model runtime, needs the owner's explicit approval.
- Anything running as the owner on a machine can read that machine's owner-only config, including a token. This is the workbench's
  own position, and the design does not claim to defend against it.

## Behavior

### What the library is

- **[agreed]** The library is the whole collection. A shelf is one domain, a book is a container for one work, and the catalog is the
  searchable set of cards. The vocabulary is in `knowledge-base.md`.
- **[proposed]** Each library has a unique id, and book and theme ids are namespaced by it. The embedding model is recorded on every
  vector. No code assumes there is only one library.

### Where things live

- **[agreed]** The library is untracked, local data, outside the clone of this project and outside every project that reads it.
  Test libraries are generated by the tooling or built from small synthetic fixtures (`testing.md`).
- **[agreed]** Config lives at `~/.config/knowledge-base/`. The library has two roots, chosen by the owner once at setup: a bulk
  root for books and an index root for databases and other small, fast data. Their defaults are under
  `~/.local/share/knowledge-base/`.
- **[proposed]** Four places hold the project's code and data. The clone of this project holds code only and can be anywhere. The
  config holds the owner-only settings: the two roots, the model registry, tokens and the approved conversion tools. The bulk root
  (default `books/`) holds originals, converted text, images and each book's manifest, and may sit on a NAS or external drive. The
  index root (default `index/`) holds the catalog and its databases, vectors, the work queue, the seen list and logs, and sits on
  fast local disk.
- **[proposed]** Search keeps working when the bulk root is absent. The index root is not a disposable cache. Cards, themes and
  descriptions are kept with their books and can rebuild the catalog, but the seen list, the work queue, the logs and, if built,
  the threads and ledger exist only in the index root, and rebuilding vectors and keyword indexes costs time. It is backed up like
  the books.
- **[agreed]** The owner's own choice of location is personal and is never a default of the project.

### The host and its clients

- **[agreed]** One library host serves all the owner's machines on the local network. Clients on other machines read the library
  through it.
- **[proposed]** The host is a resident service. It serves the interface and runs scheduled and queued work. The "no daemon" rule
  applies only to the crawler, which runs from a schedule in small batches.
- **[proposed]** The host keeps both library roots. A client's owner-only config holds the host's address and a token. No read
  command takes a path, an address or a token as an argument, and no option or environment variable changes them, even when the
  host is the same machine. The registry of models is owner-only on the same reasoning.
- **[proposed]** The interface is first a governed workbench command, and later possibly an MCP wrapper over the same operations.
  The interface offers reads and proposals only; applying a change is a governed action that runs on the host (`shelf.md`,
  "Permission levels").
- **[proposed]** The host decides. It reads its own settings and its own ceiling on every governed action, and does not take a
  client's word that an action was approved.
- **[proposed]** If the host is unreachable, a client says so, and the work in progress carries on without the library.
- **[agreed]** The library is hosted on one machine, as part of the workbench, and that machine can use various language models,
  whether hosted locally or in the cloud. The spec names no particular machine. Which machine hosts is the owner's choice at setup.
- **[proposed]** A host should be reachable whenever clients need it, have fast local disk for the index root, and be covered by
  the owner's backup.
- **[agreed]** Models may run on the host or on another machine, and the design does not prohibit either. A model on another
  machine is a compute-only client that the host calls (`knowledge-base.md`, Models). A model on the host is called the same way,
  through the same registry and router, so no stage depends on where a model runs. The library data stays on the host.

### Credentials

**Kinds and enrolment**

- **[proposed]** There are three kinds of token. A machine token enrols one of the owner's machines. A project token belongs to
  one workbench project on an enrolled machine and can be narrowed. A guest token belongs to a guest. Machine and project tokens
  are owner scope and see everything their scope allows; full text and originals need an owner-scope token. A guest token sees
  only shared shelves, and gets cards, themes, short excerpts and citation lines, but never full text or originals (`shelf.md`).
- **[agreed]** An agent never holds a machine token or the power to enrol a machine or create a guest token. An agent reads through
  a project token (owner scope, narrowable). The first token of a machine, or of a guest, is created and shown only through a
  terminal, and enrolling a machine, creating a guest token, narrowing a project and revoking a token stay at `block` in the
  workbench's permission levels. Project tokens and rotated tokens are issued by the host to the client's helper, as described
  below, and not through an agent.
- **[proposed]** A token is stored only in the owner-only config of the machine that uses it, and the host stores only a hash of each
  token. A token can be revoked at once.
- **[proposed]** The host records for each pair a name, a kind (machine, project or guest), the machine and project it belongs to,
  the dates and the expiry, and stores only hashes. Its log shows which project made a request.

**Machines and projects**

- **[agreed]** A machine is enrolled once, and each workbench project on it then gets its own pair of tokens, named for the project's
  workbench id. A guest has a pair of its own. The project's token is stored in the owner-only config of that machine, keyed by the
  project id, and nothing about it is tracked by the project.
- **[agreed]** The first time a project's helper reaches the host, the host issues the project its pair automatically, authorised
  by the machine's token, with no terminal step. A new project therefore needs no ceremony before it can use the library.
- **[agreed]** A project whose token has expired can ask for a new one while its machine's token is valid, in the same way as on
  first use, with no terminal step.
- **[proposed]** The host keeps a project's record after its token expires, keyed by project id, so a re-issued token inherits the
  scope the owner set. Without that, expiry would reset a narrowed project to full access.
- **[proposed]** Expired and revoked are different. A revoked project is marked blocked on the host, and the machine's token cannot
  get it a new token. Only the owner lifts that, at a terminal.
- **[proposed]** Every re-issue is logged with the project and the machine whose authority it used. A machine whose own token has
  expired can re-issue nothing, and is enrolled again at a terminal, after which its projects return with their saved scopes.
- **[proposed]** A project's token sees what its machine may see. Narrowing it to certain shelves is a governed action on the host,
  set by the owner, and is never taken from the project's own tracked files, which are untrusted. This is what makes a project's
  shelf list a real limit and not a hint, for the projects the owner narrows.
- **[proposed]** Revoking a project cuts that project, and revoking a machine cuts all its projects.
- **[proposed]** Per-project tokens give auditing, revocation and scope, not isolation. Every process on a machine runs as the owner
  and can read any project's token in the config, which is the position already stated above.
- **[proposed]** The project id is asserted by the client helper from the workbench project. Narrowing and audit by project id
  guard against mistakes and honest tooling, not against a hostile process on the same machine, which can read the machine token
  and claim any project id.

**Rotation**

- **[agreed]** Each token holder has two tokens, so that tokens can be rotated with no downtime. Before the **current** token
  expires, a **next** token is created. When the client has loaded the next token it becomes the current one, and the old one is
  removed.
- **[agreed]** Rotating tokens on the client is automatic.
- **[proposed]** The rotation works as follows. When the client's current token has less than a set share of its life left, for
  example a third, the client's helper asks the host for a next token, authenticating with the current one. The host issues one,
  and only one unconfirmed next token exists at a time. The client writes it to its config safely, keeping the current token
  beside it, and uses it on its next request. The host sees the first successful use of the next token as proof that the client
  holds it, makes it the current token, and retires the old one after a short grace period for requests already in flight.
- **[proposed]** The sequence survives a crash. If the client fails before saving the next token, the host's issued token goes
  unconfirmed, and the next request replaces it. If the client saved it but never used it, the current token still works until it
  expires, and both are accepted meanwhile.
- **[agreed]** Project work triggers a refresh of the machine's token when it is warranted. When a project's helper reaches the host
  and finds the machine's current token inside its rotation window, the helper rotates the machine's pair as well as its own, in the
  same way. A machine used only through projects therefore never needs a visit to the terminal to stay enrolled.
- **[proposed]** Several projects can notice the same need at once. A lock in the config makes one of them rotate and the rest
  re-read the result, and the pair is written so that a reader never sees a half-written one.
- **[proposed]** Rotation is renewal, not enrolment. The client's helper rotates by itself, in code that is not a command an agent
  can call, so it gives no capability the token did not already have.
- **[proposed]** A guest token has an absolute lifetime and is not renewed automatically; the owner renews it at a terminal.
  Automatic rotation applies to machine and project tokens.
- **[proposed]** For all tokens the host detects reuse. If a retired token is used again, or two holders use one chain of tokens, the
  chain is revoked and the owner is told in the library report.

**Expiry and loss**

- **[agreed]** All tokens expire, so that a token on a lost or forgotten machine ages out. Defaults, which are settings: 90 days
  for a machine or project token, 30 days for a guest, with a length the owner can choose when creating a guest token.
- **[agreed]** A client that stays off for longer than its token's life has lost it, and has to be enrolled again at a terminal.
  The library report lists clients whose token is close to expiry and has not rotated, so the owner sees a failing rotation
  before it locks anyone out.

### Network access

- **[agreed]** The host has an optional allow list and an optional deny list of addresses, written in CIDR notation, for example
  `192.168.10.0/24`, and the same notation for IPv6.
- **[agreed]** An allow list widens access and does not narrow it.
- **[proposed]** With no list set, the host accepts requests only from private-network addresses and from the loopback address, which
  matches the non-goal of serving the open internet. An allow list widens that: the ranges it names are accepted as well. A
  deny list blocks the ranges named. A deny entry wins over an allow entry. An owner who needs a wider range, such as a private
  network's addresses seen through a VPN, names it in the allow list.
- **[agreed]** Every network listener of the library uses the same lists, including the host interface and any later MCP server or
  other wrapper. There is one set of lists in one place, and no listener has lists of its own.
- **[proposed]** The lists are enforced in the one layer that all listeners share, before a request reaches any operation, so a new
  listener cannot be added without them. A listener that cannot apply the lists does not start.
- **[proposed]** The check runs before the token check, so a refused address learns nothing about tokens. Every refusal is logged
  with the address and the rule that refused it, and the library report counts them.
- **[proposed]** The lists live in the host's owner-only config. They are never taken from an argument, a project file or a
  client, and changing them is a governed action that ships at `block`.
- **[proposed]** The lists are defence in depth and not authentication. Addresses on a local network can be spoofed or reassigned,
  and the tokens remain the real authentication.

### Transport and listener

- **[proposed]** These are requirements only. The details are left to the builder and the security review.
- **[proposed]** Traffic between a client and the host uses TLS or an equivalent protected channel, so a token and library content
  do not cross the network in the clear.
- **[agreed]** The listener binds to an explicit address set in the host's owner-only config, never to every interface by default.
- **[proposed]** Failed token attempts are throttled, and repeated failures from one address lock it out for a time.
- **[proposed]** The address lists apply to the real peer address of the connection. Behind a proxy, the host either takes the peer
  address from a trusted proxy that the owner names, or does not accept requests through a proxy at all; it never trusts a
  forwarded-address header from an unnamed source.
- **[proposed]** A loopback listener checks the `Host` and `Origin` of each request, so a web page in a browser on the same machine
  cannot reach it.

### Setup

- **[proposed]** First setup is a governed owner action. It creates the config, chooses the two roots, writes the marker file in the
  bulk root with the library id, creates the empty catalog, and records the format version. It refuses a location that already holds
  another library's marker.
- **[proposed]** Setup is one short step that gives a working empty library, and the first shelf can be proposed straight away. The
  owner's effort to get started should be small, so that the library is fed.
- **[proposed]** Setup shows a one-time notice that rights and legality are the owner's.
- **[proposed]** The workbench module declares itself in the form its module contract requires. That is designed in the reading
  module's plan and not here.

### Moving the library

- **[agreed]** An owner who moves things can point the project at the new root locations.
- **[proposed]** Nothing stored inside the library holds an absolute path to a root: manifests, cards and the index refer to books
  by id and by paths relative to a root. So a move needs only a change to the config.
- **[proposed]** An owner-run command points the config at a new bulk root, a new index root, or both. It does not move data; the
  owner moves the files. It checks that the marker file at the new location holds the same library id, requires filing to be
  paused, switches the config in one step, and records the change. It stays at `block`, because it changes the fixed config.

### The unmounted drive guard

- **[proposed]** A guard against writing to an unmounted external volume, where a write could silently create a folder of the same
  name on the main disk. At setup the tooling writes a marker file holding the library id into the bulk root and stores the exact
  path it found. Before any write it checks that the marker is present and that the path is on a different device from the main
  disk. If either check fails it pauses filing and reports, instead of writing.
- **[proposed]** A library on the main disk, where the bulk root is on the same device, is allowed when the owner sets it so at
  setup. The device check then compares against the recorded device and not against the main disk.

### Backup

- **[agreed]** Backup and history are the owner's to arrange, and the backup itself is out of scope. The owner's own script does
  it, and the library only offers a way to pause writes while the script runs and to resume afterwards.
- **[agreed]** The flow is this. The user's script prepares the host for the backup and then calls the library's `backup-pause` command. When
  the library has paused, the command exits with no error. The script then performs its backup, which is specific to the owner's
  system. When the backup is complete the script calls the library's `backup-resume` command.
- **[agreed]** The pause has a timeout that defaults to two hours. The user's script can override the default with an argument of
  `backup-pause`.
- **[agreed]** No storage type is assumed. The design works for the worst case: a plain drive with no snapshots, copied by a
  program that knows nothing about the library, taking hours. Snapshots, where they exist, only make it faster.
- **[agreed]** `backup-pause` stops new work from starting, lets work in flight finish for a short, set time (default about
  five minutes), drops what has not finished, flushes the databases and indexes to disk, and records a backup point: the time, the
  library id, and the counts and sizes of each root. Only then does it exit 0. A result that arrives late is dropped and redone
  later, which is safe because results are idempotent (`book.md`). If the library cannot reach a quiet state, the command exits
  non-zero and the library keeps running, so the script knows not to start.
- **[agreed]** The `backup-resume` command returns each shelf to the state it had before, so a shelf the owner had already paused stays
  paused. Calling `backup-pause` while already paused extends the timeout and exits 0, which lets a long backup renew it. Calling `backup-resume` when
  nothing is paused exits 0 and says so.
- **[agreed]** If the timeout ran out and the library resumed by itself, writes may have happened during the backup. The `backup-resume`
  command then exits with a distinct non-zero status that says the pause had expired, so the script can mark that backup suspect.
  The library also says so in the library report and log.
- **[agreed]** The commands are `backup-pause` and `backup-resume`, run as `wb run knowledge-base backup-pause` and
  `wb run knowledge-base backup-resume`. The prefix avoids confusion with a paused shelf, because a library-wide resume must not
  clear a shelf the owner paused. `freeze` and `thaw` are an alternative. The timeout argument is `--timeout` with a unit, such
  as `4h` or `90m`, and `--stage` asks for the staging copy of the index.
- **[agreed]** Exit statuses: for `backup-pause`, 0 paused (or already paused with the timeout extended), 1 error, 2 bad usage, 3
  could not reach a quiet state in time and the library keeps running, 4 refused by the host. For `backup-resume`, 0 resumed (or
  nothing was paused), 1 error, 2 bad usage, 4 refused by the host, 5 the pause had already expired and writes may have happened.
- **[agreed]** The timeout the script asks for is capped by a ceiling in the owner-only config, so a script's argument cannot
  hold the library paused without limit.
- **[agreed]** The two commands are agent-safe by default, at the workbench level `none`, because a backup script run by cron or
  launchd has no terminal, and the workbench refuses an owner-run command without a terminal at `block`. A pause only makes the
  library read-only and expires on its own, so it is low risk. Every call is logged.
- **[agreed]** The owner can set either command to `block`, `ask` or `delegated` using the standard workbench permissions, to
  suit their own risk appetite.
- **[proposed]** The workbench offers these levels unevenly today (`command-permissions.md` in the workbench). An agent-safe
  command offers `block` and `none` only. `ask` is offered to an owner-run argument that declares a preview, and then its shipped
  default is `block`. `delegated` is offered only to plan approval. The first version therefore ships the two commands as
  agent-safe with `block` and `none`, and offering `ask` and `delegated` for them depends on a change in the workbench, which is
  recorded as an open question and not assumed.
- **[proposed]** To be exact about the [agreed] bullet above: the owner can choose `block` or `none` for the two commands from the
  first version, and `ask` and `delegated` only once the workbench change exists.
- **[agreed]** `backup-pause` and `backup-resume` accept the machine token only, which is a script's identity. A project token or a
  guest token is refused.
- **[agreed]** Pause renewals are rate limited, and the number and total size of the staging copies kept are capped, so a loop
  of calls cannot hold the library paused or fill the disk.
- **[proposed]** The two backup commands, and proposals, are explicit exceptions to the rule that agent-safe means reads only. A
  backup command changes the library's state (a pause) and a proposal records a suggestion, and neither applies a change to
  content.
- **[agreed]** While paused, the library is read-only and search keeps working. The crawler's scheduled runs and the pipeline's
  stages find the library paused and write nothing.
- **[agreed]** Writes are safe at any instant because filing is atomic (`book.md`), so the pause only needs to stop new units and
  finish or drop current ones. Databases are checkpointed when the library pauses, so a file copy of an index root is consistent.
- **[proposed]** The payload of a filed book is immutable and read-only: its originals, converted text, other hashed files and
  written generations are written through an incoming area and renamed into place when complete (`book.md`). Its small metadata is
  mutable: the root file, the version files, the stage state, the event log and the alternate hashes. The payload of a complete book
  can be copied while the library is live, because it cannot change under the copy. The long copy of the bulk root needs no pause.
- **[proposed]** The library publishes a list of the books that are complete, with the payload files and hashes of each. A script
  can copy those with no pause, and anything still being written is simply not in the list and is picked up by the next backup.
  The list is readable by a machine token only, has owner-only file permissions, and nothing returned to an agent contains a path.
- **[proposed]** The index root needs a pause, because its databases change while the library works, and so does the mutable
  metadata of all books. A script that wants a short pause calls `backup-pause` with a request for a staging copy. The library
  writes a consistent copy of the index root's databases and indexes, using the databases' own safe-copy method, together with the
  mutable metadata of all books, and says where it is in its library report. The script resumes at once and copies the staging copy
  and not the live files. This takes seconds to minutes, not the hours of a full copy. It costs disk space for the copy, which
  the library report shows. The staging copy has owner-only file permissions, is readable by a machine token only, and its path is
  never returned to an agent.
- **[proposed]** The simplest script pauses, copies everything, and resumes. That is the longest pause and needs the least
  knowledge of the library, so it is the default in the documentation.
- **[proposed]** A backup taken with no pause at all is survivable. The integrity check on restore discards a book that was caught
  half written (it has no completion marker), rebuilds the catalog and the indexes from the book folders, and reports what was
  lost. The payload is safe because it never changes after filing, but the mutable metadata may be caught mid-change. What cannot
  be rebuilt from the book folders is small: the seen list, the work queue, the logs, and the threads and ledger if a weave
  exists, so the staging copy matters most for those and for the metadata.
- **[proposed]** After a restore from a backup, the integrity check (below) compares the library with the recorded backup point and
  reports what differs, and the catalog is rebuilt from the book folders if it does not match.
- **[idea]** The library running the owner's backup command itself, pausing first and always resuming after. It is left out
  because the script is the owner's, and it would add a subprocess that the library runs and the security review must cover.
- **[idea]** A NAS with snapshots would answer the no-history concern for the books.

### Format version and integrity

- **[proposed]** The library records a format version, and every book carries its own (`book.md`). A newer engine opens an older
  library and reports what a migration would change. A migration is an owner-run action with a preview, and it never runs on its
  own.
- **[proposed]** An integrity check is a read-only command. It verifies the marker, the format versions, the hashes recorded for the
  files of each book, that the catalog matches the book folders, and that no manifest points to a missing file. It reports problems
  and repairs nothing. It is also what other specs call the "verify command".
- **[proposed]** The catalog and indexes can be rebuilt from the book folders alone, and the rebuild gives the same mechanical
  fields.

### The library report

- **[proposed]** A read-only library report gives the owner, and an agent with a project token (owner scope), the state of the
  library: the shelves with their states and counts, the length of the queue, the stage that is behind, the free space on each
  root, the last error, the models switched on and off, and the date of the last backup note. A guest's version of the library report shows
  only shared shelves.
- **[proposed]** The library report, the doctor and any status output computed for a guest or a narrowed token cover the visible
  subset only. Queue length, free space, last error, growth and completeness are computed over what the token can see, and an error
  never names a book the token cannot see.
- **[proposed]** The doctor, and any status output that includes host details, are for machine tokens (owner scope at the host)
  only. They contain health results only, never addresses, address ranges or registry details, because output reaches an agent and
  possibly a vendor.
- **[agreed]** The library report includes a growth forecast. For each root it shows how fast the root is growing and roughly how long
  until the free-space floor is reached, so a full disk is seen weeks ahead and not on the day filing stops.
- **[proposed]** The forecast uses the recent rate of growth, says how confident it is, and says nothing when there is too little
  history. It also shows growth by shelf, so the owner can see which shelf is using the space.
- **[proposed]** The library report lists the wanted topics from searches that found little, with their evidence, and the owner's actions
  on them (`shelf.md`, "Demand from searches").
- **[proposed]** The library report is the answer to "is the library healthy", and it needs no model.

### Retention

- **[agreed]** The usage log, the feedback notes and the used notes (`reading.md`) are each kept 180 days and at most 100 MB, are
  readable only with an owner-scope token, and can be cleared by the owner. These are defaults, which are settings.

### The doctor

- **[agreed]** The library has a doctor command that diagnoses the environment and the setup. It is distinct from the integrity
  check, which examines the data, and the library report, which shows the state.
- **[proposed]** The doctor checks that the config exists and is owner-only; that both roots are reachable and the marker and the
  device guard pass; that free space is above the floor; that the host is reachable from this client; that tokens are valid and
  rotating; that each model in the registry is reachable and whether it is switched on or off; that format versions match and no
  migration is pending; that the queue is healthy; that approved conversion tools match what is installed; that the last backup
  note is recent; that the clock has not drifted enough to break token expiry; that the address lists are sound; that an embedding
  model is installed where the registry needs one; and it warns when library content is sent over plain unauthenticated HTTP.
- **[agreed]** Each finding says what is wrong, how serious it is, and what to do about it, including the exact command that fixes
  it where there is one. The doctor only names the command and never runs it. A run with no problems says so.
- **[agreed]** The doctor is read-only and agent-safe at the workbench level `none`, and it repairs nothing. A fix is a governed
  command.
- **[agreed]** A quick run is the everyday default. A deep run also invokes the integrity check, and may take a long time on a
  large library.

### More than one library

- **[agreed]** More than one library on a single machine is deferred. A machine has one library and one config for now.
- **[proposed]** What stays is cheap: a library id, and book and theme ids namespaced by it, so that a second library, an import or
  a loan can be added later without renumbering anything. No code assumes there is only one library.
- **[idea]** Two libraries of one's own, one that never sends content to cloud models and one that may, could give an owner a
  hard separation without a per-shelf flag. This is one reason to keep the ids namespaced.
- **[idea]** Other people using the library: read-only guest tokens that see only shared shelves, or a read-only export of chosen
  shelves. Sharing captured originals is redistribution and the owner's legal question, so the derived layer (cards, themes,
  pointers) is the cleaner thing to share.
- **[idea]** Libraries interacting through an interlibrary loan, where a copy arrives as a captured item with its origin recorded.
  Vectors from different embedding models cannot be compared.
- **[idea]** Hybrid weaves, most simply by importing another library's themes, namespaced and read-only, into one's own weave.

## Acceptance criteria

All of these are provisional until the spec is approved.

- Setup creates a working empty library with a marker file holding its id, refuses a location that holds another library's marker,
  and records the format version.
- With the bulk root unmounted, filing pauses and reports and writes nothing, and search of the index still works.
- After the owner moves a root and runs the relocate command, the library works with no stored path changed, and the command
  refuses a location whose marker holds a different id.
- A client with an owner-scope token reads everything its scope allows. A client with a guest token sees only shared shelves, and
  the library report shows nothing of a private one.
- No read command accepts a path, an address or a token as an argument.
- A project or guest whose current token is near expiry gets a next token by itself, uses it, and the host promotes it and retires the old
  one, with no failed request in between.
- A client that crashes between receiving and saving a next token still works, and the next request replaces the unconfirmed one.
- A new project on an enrolled machine gets its own token pair on first use with no terminal step, and the host's log names the
  project. A project narrowed to certain shelves cannot see the others whatever its tracked files or settings say, within what the
  project token allows.
- Revoking a project stops that project only, and revoking a machine stops all of its projects.
- A project whose token expired gets a new one while the machine's token is valid, keeps its narrowed scope, and the re-issue is
  logged. A revoked project does not.
- A project's request, made while the machine's token is inside its rotation window, rotates the machine's pair too. Two projects
  doing this at once end with one valid new pair.
- Revoking a client's token stops both its tokens at once, and a client whose token expired while it was off is refused until it
  is enrolled again.
- The library report lists a client whose token is near expiry and has not rotated.
- The integrity check finds a changed file, a missing file and a catalog that does not match, and changes nothing.
- Deleting the catalog and rebuilding it from the book folders gives the same search results and the same mechanical fields.
- A migration shows a preview and runs only when the owner starts it.
- Run from a script with no terminal, `backup-pause` and `backup-resume` work at their default level, and set to `block` they
  refuse. Every call is logged.
- `backup-pause` exits 0 only when the library is paused and a backup point is recorded. Search still works while paused, and
  the pipeline, the crawler and a late model result write nothing. If the library cannot reach a quiet state, the command exits
  non-zero and the library keeps running.
- `backup-resume` returns every shelf to its earlier state, and a shelf the owner had paused stays paused. Calling `backup-pause`
  again while paused extends the timeout.
- The pause times out after two hours unless the script gives another length with an argument, and a script's length is capped by
  the ceiling in the config. When the timeout runs out, the library resumes by itself and records that it did, and `backup-resume`
  then exits with a distinct status that says the pause had expired.
- A copy of both roots made while the library is paused passes the integrity check.
- With no snapshot support, a backup made from the complete-books list and the index staging copy while the library kept filing
  restores to a library that passes the integrity check.
- A backup copied with no pause at all restores to a library whose integrity check names the half-written books it discarded and
  rebuilds the catalog from the book folders.
- The staging copy is made in a pause measured in seconds to minutes on a fixture of realistic shape, and the library report shows the
  disk space it uses.
- Every book and theme id carries the id of its library.
- With no lists set, a request from a public address is refused and logged, and one from a private address is accepted. A deny
  entry in CIDR notation blocks an address inside it even when an allow entry covers it. The refusal comes before any token check.
- A second listener, such as an MCP wrapper, refuses the same addresses as the host interface, and a listener that cannot load the
  lists does not start.
- The library report shows, for each root, its growth rate and the estimated time until the free-space floor, and shows no estimate when
  history is too short. Growth by shelf adds up to the growth of the root.
- The doctor reports a missing or world-readable config, an unreachable root, a failing marker check, low free space, an
  unreachable host, a token near expiry, an unreachable model, and a pending migration, each with what to do. It changes nothing.
- A guest token is not renewed automatically and expires at its absolute lifetime. A retired token used again, or one chain used by
  two holders, revokes the chain and appears in the library report.
- `backup-pause` and `backup-resume` refuse a project token and a guest token, pause renewals are rate limited, and the staging
  copies kept are capped in number and total size.
- A backup copy of a filed book's payload taken while the library is live is complete, and the staging copy holds the mutable
  metadata of all books.
- For a guest token or a narrowed project, the library report and the doctor are computed over the visible subset only and name no
  book the token cannot see. The doctor shows health results only, with no address, range or registry detail, and only to a machine
  token.
- The table of actions lists every action named in the specs, and an agent-safe action ships at `none` while every other action
  ships at `block`.

## Open questions

- The form of the host interface, which is for the builder and the security review. Whether the interface is a small local service
  or a command that reaches the host some other way.
- How a token is made (its length and source of randomness), the share of life left that starts a rotation, and the length of the
  grace period for the retired token.
- The form of the format version, the migration and the integrity check in detail.
- The wait for work in flight when a pause is requested (about five minutes is proposed).
- The gate that `delegated` uses for a governed shelf or library action, and how the owner gets `ask` and `delegated` for the
  backup commands as well as `block` and `none`. It needs a change in the
  workbench's permission levels: an agent-safe key that can offer `ask` while keeping a default of `none`, and a gate that
  `delegated` could use for a pause.
- Which backup tools to document with worked example scripts. The script is the owner's, and the examples only show the calls.
- How the complete-books list is expressed so that an ordinary backup program can use it (a file list, an include file, or a
  folder of links, noting that the workbench refuses symlinks).
- How much disk the staging copy needs at the expected scale.
- Whether the staging copy, which holds the seen list, logs and queue, is kept or deleted after a backup.
- How the workbench would treat a local model, a plain-completion bridge and an MCP layer. These are workbench questions.
- Which checks the doctor runs in a quick run and which only in a deep run, and the form of its output for a script.
- Whether IPv6 needs any special handling beyond CIDR notation, and how addresses are read when the host sits behind a proxy.
