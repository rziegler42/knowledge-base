# Testing

Status: Draft

This specifies how the knowledge base is tested: the test libraries and fixtures, how stages that use a model are tested, the
evaluation runs that measure quality, and the checks that the safety and privacy rules hold. It belongs to the design in
`knowledge-base.md`; the acceptance criteria it gathers are in `book.md`, `theme.md`, `shelf.md`, `card.md`, `library.md`, `pipeline.md`,
`models.md`, `reading.md` and `weave.md`. **Nothing here is final.** The spec stays `Draft` until the owner approves it, and any statement can be reopened. Each statement carries one of three
marks:

- **[agreed]** The owner said it. It is the working position and it can still change.
- **[proposed]** The assistant's suggestion. The owner has not decided it.
- **[idea]** Exploratory. It is recorded so it is not lost, and it is not a requirement.

## Scope

How the engine is shown to work and how its quality is measured. This spec covers the shared fixtures, the ordinary test suite, the
live-model evaluation, and the groups of checks the other specs depend on: filing, versions, permissions, privacy, safety, restart
and relocation. It does not cover how a plan's increments are verified in the workbench, which the workbench's own rules govern.

## Non-goals

- **[agreed]** Committing data. Only the engine (code, specs and documents) is ever committed, so a test never relies on a real
  library, and no test file holds fetched papers, personal questions or a real card.
- **[proposed]** Proving that the library finds novel concepts. That is a judgment over time. The tests show that the mechanisms
  work and measure what can be measured.
- **[proposed]** Testing a model's quality in the ordinary suite. A model's quality is measured by the evaluation, not by a test that
  can fail because a model changed.

## Assumptions and constraints

- Test libraries are generated by the tooling or built from small synthetic fixtures (`knowledge-base.md`).
- The ordinary suite needs no network, no model server, no real library and no secrets, and it runs on any machine that has the
  clone.
- The workbench's rules for tests apply: a test is written before the code it covers and is seen to fail for the right reason
  (`test-first`), and nothing is reported as passing without the check being run.
- Everything fetched or generated in an evaluation run is untrusted data and stays outside the repository.

## Behavior

### The two layers

- **[agreed]** Stages that use a model are tested in two layers. Ordinary tests use recorded sample model outputs kept as small
  synthetic fixtures. A separate evaluation, started by the owner against a live model, measures quality, and its results are never
  part of the ordinary suite.
- **[proposed]** A recorded output is stored with the stage, prompt version and fixture it answers, so a test that feeds it to the
  stage checks parsing, validation, storage, indexing and failure handling, and does not check what the model would say.
- **[proposed]** When a prompt version changes, its recorded outputs are marked out of date, and the suite says which fixtures need
  new recordings. A recording is refreshed by an owner-started run and reviewed before it replaces the old one.

### Test libraries and fixtures

- **[proposed]** A generator builds a small library in a temporary directory with its own library id, bulk root and index root, so
  tests exercise the real layout (`knowledge-base.md`, "Where things live") and delete everything afterwards.
- **[proposed]** The standard fixture library has three shelves, A, B and C, each with a few synthetic books, and a problem D whose
  combined solution is known: a method from each shelf is needed. The text is invented, short and written to have a known
  structure, and uses invented names, so it cannot be mistaken for a real work.
- **[proposed]** There are also fixtures for the awkward cases: a preprint and its published version, a source with its own version
  labels, a near-identical re-upload, a pointer-only item, a book with no structure, an encrypted file, a file with embedded
  script, a file with text that tries to give an agent instructions, a source that refuses with a login, and a source that holds
  the same work at another address.
- **[agreed]** Fixtures are both static and generated. The awkward cases are small static files in the repository, each readable and
  exact. The standard A, B, C library, and anything needed at scale, is built by a generator so many books can be tested without
  committing them.
- **[proposed]** No fixture, static or generated, is a copy of a real paper or page.

### Groups of checks

Each group names what must hold. The other specs hold the detail.

- **[proposed]** *Filing and layout.* A book is filed atomically: a crash at any step leaves no half-written book, and a restart
  resumes. Files are read-only afterwards and the integrity check finds a changed one. A reshelve moves no bytes and changes no id.
- **[proposed]** *Versions.* The version rule gives a new version for a meaningful text change, a sighting for a trivial one, and one
  book or two for a preprint and its published form. Re-running a task on the same book version, task, prompt version and model
  is idempotent.
- **[proposed]** *Pipeline.* Stages run as soon as their input is ready, bounded queues hold, a restart resumes from the manifest,
  and a search says how complete its source was while a shelf is still being seeded.
- **[proposed]** *Permissions.* Each governed action refuses at `block` without a terminal, runs at `ask` only with the digest of
  the exact preview, and runs at `none` with a log entry. A changed rules file does not match an old digest, and an agent cannot
  apply a proposal. The host's ceiling overrides a looser client level.
- **[proposed]** *Privacy.* The check applies to every token kind. A guest's search, count, thread, hint and error message never
  reveal a private shelf, including its name, scope and size. This is tested by comparing a guest's results, and those of a
  project narrowed on the host, on a library with and without the private shelf, which must be identical. The comparison extends to
  the library report, the doctor, errors, the answered notice, aliases and cross-book links.
- **[proposed]** *Crawler destinations.* The crawler refuses private, loopback and link-local destinations, and revalidates the
  destination of every redirect.
- **[proposed]** *Guest limits.* A guest's cumulative excerpt reads are capped.
- **[proposed]** *Converters.* A converter that is not sandboxed is refused approval.
- **[proposed]** *Token reuse.* A retired token used again, or one chain of tokens used by two holders, revokes the chain and is
  reported in the library report.
- **[proposed]** *Guest tokens.* A guest token is not renewed automatically and stops working at its absolute lifetime.
- **[proposed]** *Safety.* A hostile fixture is filed inert and carries a caveat. Conversion respects its time and size limits and
  has no network. Nothing returned to an agent lacks the untrusted marking, and an instruction inside content does not change what
  a stage does.
- **[proposed]** *Crawler.* Against a local test server, the crawler honours its per-site speed, sends its configured headers,
  follows its refusal handling without bypassing a login, a paywall or a CAPTCHA, and records the refusal. The ordinary suite never
  touches the network.
- **[proposed]** *Relevance and placement.* Candidates near the threshold are kept on the seen list with a score and reason. A tie
  between a shared and a private shelf goes to the private one. A new shelf proposes moves only for books that fit it clearly better.
- **[proposed]** *Relocation.* After the owner moves a root and runs the relocate command, the library works with no stored path
  changed, and the command refuses a location whose marker holds another library id.
- **[proposed]** *Rebuild.* The catalog and the indexes can be rebuilt from the book folders alone and give the same search results.

### Evaluation

- **[proposed]** The evaluation is a command the owner starts. It runs the stages against a live model on the fixtures and,
  if the owner supplies one, on a corpus held outside the repository, and writes a report outside the repository.
- **[proposed]** It measures: the share of themes whose anchors hold; themes per thousand tokens and near-duplicates; leaks of field
  vocabulary into neutral descriptions; the rank of the right book or theme for a set of questions, by card, by summary and by
  neutral description; and the recall of the standard fixture, where searching the sub-questions of problem D should surface a
  theme from each shelf.
- **[proposed]** A set of questions with known answers can be kept in the repository only if it is synthetic. A set drawn from the
  owner's own projects stays outside it, and a summary of results may be written into a spec only when it names no personal
  project, path or machine, with a provenance line.
- **[proposed]** The evaluation reports a number for a stage and never fails a build. A change that lowers a measure is a finding
  for the owner to weigh.
- **[proposed]** The same evaluation is used to compare two models or two prompts on the same inputs, so a change of model or prompt
  is justified by a measure.
- **[proposed]** The cross-field transfer set is the standard evaluation of cross-field retrieval. It uses documented transfers as
  ground truth: annealing from statistical physics into combinatorial search, bandit methods into game-tree search, sequential
  testing into engine matches, foraging theory into search stopping, epidemic spreading into information spread, immune systems into
  anomaly detection, ant trails into routing, and visual cortex models into image recognition, plus a composite problem that needs
  three of them. The source papers, the measures and the queries are fixed and hashed before any search runs, the queries are
  written by an agent that never sees the corpus, and each problem is stated in the target field's own words in four forms. The
  measures are the rank of the first source paper and theme, recall at 5, 10 and 20, how often one book is a hub, and whether each
  composite sub-question reaches its source shelf. The papers are fetched from public sources at run time and never committed. The
  first run is summarised in evidence note 10 of `knowledge-base.md`.
- **[idea]** A second corpus with more variety than the first, because the first extraction test was small and mostly one field.
  The transfer set has 4 to 8 papers per shelf and eight transfers, so a larger one with held-out queries would settle what it could not.

### What the suite does not prove

- **[proposed]** Passing the ordinary suite shows that the mechanisms work on invented text. It does not show that the cards and
  themes are good, that the relevance threshold is right, or that the library surfaces useful ideas. Those are the evaluation's and
  the owner's judgment, and the specs say so where they rely on them.

## Acceptance criteria

All of these are provisional until the spec is approved.

- A fresh clone runs the ordinary suite with no network, no model server and no real library, and it passes.
- The standard fixture library is generated by the tooling and removed afterwards, and no fixture is a copy of a real work.
- A stage fed a recorded output stores, indexes and validates it, and rejects a malformed or oversize one.
- Changing a prompt version marks its recordings out of date and the suite names the fixtures to refresh.
- The privacy check passes for every token kind: the results of a guest, and of a project narrowed on the host, with and without
  a private shelf are identical.
- The permission checks pass at `block`, `ask`, `delegated` and `none`, including a stale digest, and `delegated` reads as `block`
  until a gate is defined.
- The evaluation reports the measures above without changing the library and without failing the suite.

## Open questions

- How realistic synthetic text must be to make a retrieval test meaningful.
- How a recording is refreshed and reviewed so that a bad recording does not hide a real defect.
- How large the standard fixture library must be to make the cross-shelf recall check mean something.
- Where an owner-supplied evaluation corpus lives and how its use is kept out of the repository by default.
- Whether the crawler's local test server ships with the engine or is built by the tests.
- The choice of test framework, left to the builder.
