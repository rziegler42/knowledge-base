# Show the state and the report of the unattended crawl: `crawl-status` and `crawl-report`

Status: In Progress
Created: 2026-11-16
Candidate: none (the crawl is specified in `docs/specs/population.md`, which the owner approved as the design to build; the two commands are its "Status and the report" section and its acceptance criterion 19, and are too small to need roadmap direction)
Specs: docs/specs/population.md

## Goal

The owner needs to see what the unattended crawl is doing and has done, without a command that can change it. This plan builds the two read-only commands of the spec's "Status and the report":

- **`crawl-status`** prints the state (*running*, *idle*, *paused*, *stopped*), the counts of the candidate queue by status for today and in all, the counters of the day against the ceilings, the last run, the free disk against the floors, the lists in use and their age, and the reasons of the most recent rejections, failures and holds.
- **`crawl-report`** writes the report of one day: how many were fetched, kept, rejected and failed; every book filed, by address and host; the books moved by the model's pick and the shelves; the books left on `default` for want of a shelf; the books held by the scan; the works rejected for their type; every pause of the circuit breaker; every list that could not be refreshed; the count of books unreviewed by the owner; and the failures by reason.

When it is done: both commands run against hand-made fixture files in the spec's log format and against a fixture library, print or write every field the spec lists, make no network request and no model call, change nothing in the library, the queue or the log, and print no text from the web that has not been redacted and cleaned. **The runner does not exist yet** (another plan builds it on the macOS machine), so the fields that only the runner writes are checked against fixtures only; the Result names them. The reader of the approved plan (`crawlplan.read_plan`) is built first by the runner plan: until it is on `main`, this plan takes it as an injected function, and the last increment wires the real one.

## Scope

- `engine/kb/crawlstatus.py` (new): the reading of the files the runner and discovery leave in the index root, and `crawl-status`.
- `engine/kb/crawlreport.py` (new): `crawl-report`.
- Their tests and fixtures (`engine/tests/test_crawlstatus.py`, `engine/tests/test_crawlreport.py`, `engine/tests/fixtures/crawlstatus/`).
- In `engine/kb/__main__.py`, **only the registration of the two commands**: one contiguous block of parser lines and one contiguous block of dispatch lines, with the module import inside the dispatch block, so that no other line of the file changes and the merge with the runner plan (which also adds commands there) touches as little as it can.

## Non-goals

- The runner, the approval command, the stop and breaker files' writers (`crawl-run`, `crawl-approve`, `crawl-clear`): another plan.
- **A reader of the crawl plan.** The owner's instruction is that this plan writes no second plan reader: `crawlplan.read_plan(path)` is the only one, and it belongs to the runner plan.
- Any change to `crawlqueue.py`, `weblists.py`, `urlhaus.py`, `placereview.py`, `store.py`, `catalog.py`, `discover.py`, `crawlplan.py` or any other module: they are read and called, never edited. The files that the plans F and R own (`capture_url.py`, `capture_arxiv.py`, `store.py`, `placement*.py`, `placeapply.py`, `webaddr.py`, `webclient.py`) are not edited.
- Writing the log, the queue, the lists or a book. The only file either command writes is the report, and only `crawl-report` writes it; **nothing is ever written into `crawl/log/`.**
- A summary across all the days of the crawl, per-shelf and per-site breakdowns (the spec lists them as built later), a web page, mail or any push of the report anywhere.
- Running the macOS-only parts: this machine is Linux. The code is portable Python with no macOS-only call; what could not be checked on macOS is named in the Result.

## Assumptions and constraints

- **The formats are used as the spec and the owner's instructions give them:** the log (`<index root>/crawl/log/crawl-YYYY-MM-DD.jsonl`, one JSON line per action with `ts` (UTC), `run`, `step`, `outcome`, `candidate`, `book`, `host`, `reason`, `n`, `seconds`; the steps and outcomes the spec lists), `candidates.sqlite` and its `counters` table (read with `PRAGMA user_version` 1 and the exact table shape that `crawlqueue` checks), the run lock `crawl.lock`, the stop file `crawl.stop`, `crawl/breaker.json` and the events `crawl_found`, `crawl_rejected`, `crawl_held` and `reshelved` of a book's own event log.
- **Every address, title, host, shelf and reason that is printed or written came from the web, or from a model, or from a file that anything with write access to the index root can change.** It is untrusted. It goes through **three steps, in this order**, before it is printed or written: (1) **normalise**: `placereview.safe` at a fixed generous bound (2,000 characters; it is the cleaning of `place-review`: control, format, line, invisible and bidirectional characters and long runs of combining marks removed, white space collapsed), so that the text is the one a reader would see, with no hidden character left to split a name; (2) **`redact`** (a fixed rule, below) on that normalised text; (3) **cut** to the field's length, last, so that a cut can never leave half of a key that the rule would have withheld. A text over 2,000 characters is cut at step 1 and the rule looks at what is left; the output is cut shorter still. The commands read no key file, no header and no environment variable, and no log field is copied except by name (see Risks).
- **The redaction rule (`redact`)** is applied to every text field, before it is cleaned and cut, and is a safeguard against an accident and **not a guarantee**: the spec's rule that the log, the report and the queue never contain a key or a header stays the runner's first line. (a) A value in which one of the names `Auth-Key`, `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key` or `X-Auth-Token` appears (any case, followed by optional spaces and `:` or `=`), or the word `Bearer` followed by a token, is **withheld whole**: it is shown as `[withheld: looks like a header or a key]`. (b) In an address, the user and password before an `@` are removed, and the value of a query parameter named `key`, `apikey`, `api_key`, `token`, `access_token`, `auth`, `secret`, `password`, `passwd`, `sig` or `signature` is shown as `[withheld]`. A text that no rule matches is shown cleaned, as any text; the module cannot know a key by its look, and says so in its docstring and in the Result.
- **The reading is bounded and strict.** A file is opened without following a link and without waiting on a pipe, must be a plain file of the owner's, and is read up to a fixed size; a log line is parsed as JSON with no duplicate key and no non-finite number, its known fields are type-checked, its step and outcome must be in the spec's lists; **a bad line is skipped and counted** (the count is printed), and a file over the size is read up to the size and said to be cut. A fault of one file is a line in the output, never a crash and never a refusal of the whole command.
- **Read only means:** no network, no model call, no write to the library, the queue, the log, the lists, the lock or a book. `crawl-status` opens the queue read-only (`mode=ro`), opens `crawl.lock` without creating it, and takes **one non-blocking shared `flock` attempt, released at once** (never held while anything else is read). `crawl-report` writes exactly one new or replaced file, its own report.
- **The owner's instructions of 2026-11-16, which this plan follows, and the decisions it proposes where the spec is silent:**
  1. **The report's path** is `<index root>/crawl/report/crawl-report-YYYY-MM-DD.md` (the owner's instruction): plain Markdown, the file mode 600, the folder `crawl/report/` mode 700, written to a temporary file in that folder and renamed into place. **Nothing is written into `crawl/log/`**, and the report appends nothing to the log. Running the report for a day again replaces that day's file. **Because a Markdown viewer renders what it is given, every text from the web, a model or a file is written inside an inline code span, after redaction and cleaning, with its backticks, pipes and angle brackets replaced**, so that an address or a reason cannot make a link, an image, a heading, a table cell or HTML in a viewer.
  2. **"Both commands only read" is read as "neither changes the library, the queue, the log or the lists"**; the report file is the report's own output and is the one thing `crawl-report` writes.
  3. **The approved plan's values** (the ceilings, the floors, the timezone and the lists that are on) come from the approved copy: `<index root>/crawl/approved/current` holds one line, the digest, and the copy is `<index root>/crawl/approved/<digest>/plan.txt` (the folder also holds `topics.txt`, `allow.txt`, `fingerprint` and `summary.txt`, which are not read here). **The files this plan reads are the contracts of the section "Interfaces the other plans build against" of `docs/plans/2026-11-16-build-the-safeguards-of-the-unattended-crawl.md` (the runner's guard rails, plan R1; a change to them needs the owner), and where the two plans differ, that one governs the file and this one is corrected.** **The reader is `crawlplan.read_plan(path)`, built first by that plan's Increment A; this plan writes no second reader.** Until `crawlplan` is on `main`, `crawlstatus` takes the reader as an argument (`read_plan`), and the tests give it a function that returns a **fixture dict**; the shape of that dict (the plan's keys, flat, as `discover.read_plan` returns them) is an assumption that the last increment checks against the real reader and, if it differs, adapts in one place. If `current` is missing, is not one line holding a digest, or names a folder that does not exist (or holds no `plan.txt`), the status says **"no approved plan"** and shows the counters without ceilings; the floors, the timezone and the lists then take the spec's defaults, said so.
  4. **The counters** are the rows of the `counters` table with the keys `fetch`, `fetch:<registrable domain>`, `card` and `refusal:<registrable domain>`, and the day as `YYYY-MM-DD` **in the plan's timezone** (the owner's instruction). They are shown against `fetches_per_day`, `per_domain_per_day` and `cards_per_day` (a `fetch:<domain>` row against `per_domain_per_day`); the `refusal:` rows are shown as counts, with the plan's `domain_refusals` printed beside them (the runner plan's `site_stopped` decides when a site is stopped for the day; this module does not, and does not repeat that rule). **`filed_total` is not a counter:** it is the number of books with a `crawl_found` event, counted by reading the books (Increment C), and is shown against the plan's `filed_total`. Every other row of the day is printed as it is; discovery's own rows (`source_off:<name>`, `web_search_queries`, which use a UTC day) are shown as discovery's, and its `walked:` rows (day `permanent`) are only counted.
  5. **Which day a log line belongs to is read from its `ts`, not from the name of its file.** The files are named by UTC day, and "today" in the status output is a day in the plan's timezone (`local`, or an IANA name; `local` is the machine's zone), so a local day can lie in two or three UTC-day files. The module reads every file from the UTC date of the day's start to the UTC date of its end (and nothing outside that range), keeps the lines whose `ts`, in the plan's zone, falls in the day, and the same for the report's day. Today's counts by status are the queue rows whose `updated` falls in that day (converted to UTC, so that a day of 23 or 25 hours is right). The report prints the first and last `ts` it kept.
  6. **Last run and run counts come from `run_start` and `run_end` lines only.** The last run is the run whose `run_start` has the newest `ts`, with the `run_end` of the same `run` if there is one (none: "no end line"). A `refuse` line, in particular one whose reason is "a run is in progress" (a firing that found the lock held), **is not a run**: it changes neither the last run nor the number of runs. Refused firings are counted apart, by cleaned reason, so that the owner sees them and they are never taken for runs.
  7. **The state when more than one holds:** *stopped* if the stop file exists, else *paused* if the breaker says so (assumption 8), else *running* if the lock is held, else *idle*; the three facts are also printed each on its own, so a run that is finishing its step while the stop file exists is shown as both.
  8. **When the breaker says paused (the owner's correction).** `crawl/breaker.json` always exists once a plan has been approved, and it reads as *not tripped* **only when it says `"tripped": false`**. *Paused* is shown when the file **is missing** (before any approval it always is, and the status then also says no plan is approved), **cannot be examined** (`lstat` fails for a reason other than the file being absent), **cannot be read** in the form of the runner plan's contract, `{"tripped": <true|false>, "reason": <text, at most 300 characters, or "">, "kind": <consecutive_failures, failure_share, model_down, stage_bound, or "">, "at": <a UTC time YYYY-MM-DDTHH:MM:SSZ, or "">, "run": <text or "">}` (not a plain file, a link, a folder or a pipe, over the size, not UTF-8, not JSON, not an object; **a key of the five missing**; a `tripped` that is not a JSON boolean; a `reason`, `kind`, `at` or `run` that is not text, **including `null`**; a `reason` over 300 characters; a `kind` that is not one of the four or empty; an `at` that is not a UTC time or empty; any other key is ignored and not shown), **or says `"tripped": true`**. Each case is printed with which it was (`missing`, `cannot_examine`, `cannot_read`, `tripped`; a file that says `false` is `not_tripped`), and for a tripped file the `reason`, `kind`, `at` and `run`, redacted and cleaned. **This reading is stricter than the first draft of this plan, which allowed the four texts to be absent or `null`: the contract says they are always written, and a file in another form is by that contract an unreadable one, which pauses.** The spec's older text for *paused* ("the breaker file exists", "A missing or unreadable breaker file is read as tripped") is corrected by the runner plan's Increment A, not by this plan.
  9. **The lock** `crawl.lock` is opened without being created, and one non-blocking shared `flock` is tried and released at once. **If another process holds it, the state is *running*.** The runner writes one line while it holds the lock, `<pid> <YYYY-MM-DDTHH:MM:SSZ>`; the module reads at most 256 bytes of it, **only when the lock is held** (a line left behind by a run that is over is not read), and prints the pid and the start time when the line matches exactly. **If the line is missing, empty or malformed, the state is still *running* and the holder is printed as `unknown`**; no pid is checked for being alive.
  10. **The folder of the lists** is `<index root>/crawl/lists/`; `weblists.Matcher` and `urlhaus.Source` take their folder as an argument, so the runner decides, and the name is one constant here (for both). For the two public lists the module reads only the small record (`<name>.meta.json`), never the list itself, and checks that the data file it names exists with the recorded size; **it does not recompute the hash** (the matcher does that when it uses the list), and says so. **For URLhaus recent mode** (`urlhaus.py` on `main`, which keeps its state in `urlhaus.json`: `version`, `last`, `off_day`, `entries`) the module reads that file, up to 64 MiB (a larger file is not read: its size is printed and the fields are unknown), and prints whether the plan has it on, the time of the last request and its age, whether the source is **off for the day** (`off_day` is today's UTC day), the number of kept URLs and the newest date among them, and whether the file is damaged (the source then makes no request that day, which the module's own text says). **It prints no URL, reads no key file and checks no key**: the key's path is not read and its existence is not tested.
- **The text rule** is `placereview.safe(value, limit)`. It is imported, not copied, so that the report and `place-review` clean text the same way; the plan notes that this ties the module to the name `safe` in that file.
- **Platform:** `fcntl.flock`, `os.statvfs`, `os.O_NOFOLLOW`, `os.O_NONBLOCK` and `zoneinfo` exist on Linux and macOS and are used as `store.py` and `crawlqueue.py` already use the first four; no `/proc`, no `os.sched_*` and no Linux-only flag. `zoneinfo` needs the system's zone files, which both have.
- **Method:** as `AGENTS.md` says: tests first, seen to fail; deliberate breaks of the new modules (each file restored byte for byte, equivalent mutants named); the project's `reviewer` agent for each increment; a Result for each; `wb run code-work check`; one local commit for an increment on the owner's word; no push.
- **Tests run with a temporary index root**, an injected clock, an injected `statvfs`, an injected plan reader and fixture files in the spec's formats; **they never read the owner's library, config, plan, topics or keys.**

## Risks and sensitive actions

- **The files read are untrusted at every field.** The log is written by a process that reads pages from the web, and its `reason`, `host` and `candidate` can hold text from them; the books' events and root files can be changed by anything that has write access to the library; a queue row's address and reason came from the web; `breaker.json` and the lock's line are files in the index root. The mitigations: strict, bounded, no-follow reads; a known-field copy; `redact` and `placereview.safe` on every printed or written text; the code span in the report; and tests with hostile text in every field. **The owner has asked for a security review of this surface** (it parses files that untrusted text reaches, redacts them, reads the queue read-only and writes the report file): it is run with the `security-reviewer` agent **after Increment E is built and reviewed**, on the code of Increments A to E, with experiments on a copy (hostile log, queue, breaker, lock and event files; links, pipes and oversize files; split and hidden-character headers; Markdown and HTML in every field; the report path and the folder's permissions); its findings are decided with `evaluate-findings`, fixed test first, and recorded in the Result, and a second look at the fixes is part of the run. The review is not asked again for Increments F and G unless they change how input reaches a privileged use.
- **No key or header is printed.** The commands read no key file, no environment variable and no header; the log's fields are copied by name from a fixed list, so a field that the runner should never write cannot reach the output. A key in a log field that is on the list (a `reason` that holds one) is caught by `redact` only when it has a header name, a `Bearer`, or a parameter name of the list around it; **a bare key with nothing around it is printed as text**, so the spec's rule that the log never contains one is the runner's to keep, and the Result says so. The URLhaus key's file is never opened and its path is never read.
- **The shared lock attempt can, for an instant, make the runner's own attempt fail.** The runner takes `LOCK_EX|LOCK_NB` on `crawl.lock` and exits quietly if it is held; during the microseconds of this module's `LOCK_SH|LOCK_NB` attempt, a runner starting at that instant would exit as if another run held the lock, and the next firing would start it. This costs one firing at most and is accepted by the spec's own words ("a non-blocking shared `flock` attempt released at once"). It is the only way a command here can affect the runner.
- **Opening a WAL database read-only can create its `-shm` and `-wal` side files** if they do not exist. They are the one permitted change to the index root (criterion 4), and Increment C measures what SQLite does here first. If a read-only connection cannot read a WAL queue at all, the counts are printed as unknown and the question comes back to the owner; the module does not turn to `immutable=1` (it ignores the WAL and can show a stale or torn count). What SQLite does on macOS is not measured and is named in the Result.
- **The report is one file in a folder the plan makes.** It is replaced by a rename. It holds addresses of the web pages the library took in, which the owner may not want in a shared folder: the folder is mode 700 and the file 600. Its text is written so that a viewer cannot be made to render what the web sent.
- **The status reads every book's root file** to count `filed_total` and the unreviewed books. That is a read of the whole library's small files on each run of the command; it is bounded (200,000 books) and reads an event log only for a book that is `auto_filed`.
- **The `reshelved`, `crawl_found`, `crawl_rejected` and `crawl_held` events, `auto_filed`, the log's `candidate` field, the lock's line and the form of `breaker.json` (`tripped`, `reason`, `kind`, `at`, `run`: the runner plan's contract), the counters' keys and the fixture dict's shape for `crawlplan.read_plan` are not yet written or built by any code on this branch.** The fixtures stand in for them; if the runner differs, a field is shown as unknown or counted bad and not guessed at.
- **This plan depends on the contracts of the runner plan R1** (`docs/plans/2026-11-16-build-the-safeguards-of-the-unattended-crawl.md`, "Interfaces the other plans build against"), whose status is `Proposed` and whose code is not built. If the owner changes a contract (the lock's line, the breaker's form, the counters' keys, the approved folder's names, the log's day), the matching part of this plan changes with it; `crawl/guard.json` (that plan's record of when the model server was first seen down) is not read here.
- **The merge of `main` in Increment G** brings in other plans' work. It is local, and stops if the reader is not there; it changes no file that this plan does not own except through the merge itself.
- **Nothing is committed, pushed, installed or deployed by the plan** beyond the local commits of its increments on the owner's word; no dependency is added.
