# Load PDF files from the owner's disk into the library with a command

Status: Proposed
Created: 2026-11-19
Candidate: none (work too small to need roadmap direction: it adds the one way into the library that the pipeline lacks, and the pipeline spec already treats every captured book alike; the owner's request, 2026-11-19: a folder of about 60 PDF files to load)
Specs: docs/specs/pipeline.md ("Safety of captured content"), docs/specs/library.md

## Goal

Nothing loads a file from the owner's disk into the library. `capture-url` and `capture-arxiv` fetch over the network, and the crawl fetches what it finds. The owner has a folder of 61 PDF files (about 1 GB) of electronics books and handbooks, and wants them in the library.

Measured on 2026-11-19, read only, by a script of Python 3.15.0 that printed counts and names, at commit `68bf7b7` of `main`, on `/Volumes/Data/Restored Data/Electronics ebook collection (reseeding)`: 64 files, no subfolders and no links; 61 begin with `%PDF-`; the other three are `.DS_Store` and two `.zip` files; the largest PDF is 92 MB and none is over 100 MB; the total is about 1 GB; two pairs are the same bytes under different names (the two *Electronics for Dummies*, the two *Teach Yourself Electricity & Electronics*); four carry an `/Encrypt` mark in the first or last 4 KB; none of the 61 is already in the library by its content hash.

When this plan is done, **`kb capture-file <path> ...` takes each PDF file (or each `.pdf` file directly inside a folder) and files it as a book of the owner's**: a book of the kind `paper` on the shelf `default`, not marked `auto_filed`, with the file as `paper.pdf`, its content hash as an identity key, a `filed` event and the stage `fetched` done; a file whose bytes the library already holds is not filed again. The existing steps (`kb process`, the cards, the placement, and the themes that the idle window of the crawl makes) take it from there, as for any book.

## Scope

- A new module `engine/kb/capture_file.py` (the capture of one file) and its tests; the command `capture-file` in `engine/kb/__main__.py`, with tests in the existing test file of the command line.
- `docs/specs/library.md` or `docs/specs/pipeline.md` says what the command does (read at Increment A, step 1, to choose the place); the plan's Result.

## Non-goals

- Any file that is not a PDF: HTML, EPUB, text, and the two `.zip` files of the owner's folder (the owner unpacks them to a folder of their own, and the command is run again).
- A walk into subfolders; a limit of the folder size; any change to `capture_url.py`, `capture_arxiv.py`, the scan, the conversion, the cards or the crawl.
- Reading the PDF's own title, authors or year: the title is the file name without `.pdf`, cleaned; a later step may do better (a todo item records it).
- Moving or deleting the owner's files. The command only reads them.
- Marking the book as the crawl's: nothing in the crawl's steps (judge, proposal, move) touches a book that is not `auto_filed`, and the owner places these books with `place-propose` and `place-review`.

## Assumptions and constraints

- A file is untrusted data, though the owner chose it: it may be a PDF made to attack a reader. The command **reads and stores bytes and never parses the PDF**; the scan and the conversion read it later, in the sandbox with a limit on memory, time and file size that exists for every captured PDF (`convert_run`; a PDF is never converted without a limit).
- The command refuses a path that is a symbolic link, is not a regular file, or is reached through a link in its last component, and opens a file with the flag that refuses a link (`O_NOFOLLOW`) and reads at most one byte more than the size limit, so that a file that grows while it is read, or a special file such as a pipe, cannot hang or fill memory.
- The size limit is an argument of the command, `--max-bytes`, with the default 100 MB (a PDF over it is refused, not cut). The converter's own limits apply later.
- **A duplicate is told by an atomic claim, not by a look alone.** The identity index is a table with the primary key (kind, value), and `Identity.register` is an `INSERT OR IGNORE`: the first book to claim a key keeps it. The order for one file is: (1) look up the hash; a holder that **exists and is `active`** makes the file a duplicate with nothing written (the usual case, and the only one that costs no write; note that the helper `_live` of `capture_url` only asks whether the book exists, so it is not used here: a weeded book is not a holder); (2) with no live holder, **make the book first** (its root file, with the hash among its identity keys, so that the book is live when it can be found); (3) **claim the hash for it with `register`** and read who holds it; if the holder is another live book (a run that claimed in between), the new book is set `weeded` with a `capture_failed` event and the file is a duplicate; an entry that names a book that does not exist, **or a book that is not `active`** (the book that this very command weeded after a failure, or one weeded by the owner), is taken over with `reassign`, so that a retry owns the key and the next call reports a duplicate; (4) file the payload, the version, the stage and the event. A book that the index names and whose stage `fetched` is not done (a run that died after the claim) is finished with this file, and no second book is made. An error of any kind, a stop by the owner included, after step 2 sets the new book `weeded` with `capture_failed` before it leaves. **Two runs of this command** are kept apart by an exclusive, non-blocking `flock` on a file in the index root that the command holds for its whole run (the way the queue of the cards is locked): a second run is refused with a fixed reason. **The crawl's capture does not take this lock**, and the plan does not change it. It meets the claim in the index: once the book is claimed it is a live book of the owner's, and the crawl's capture answers `held` for it (`capture_url` returns `held` for a live book that is not the crawl's) and writes nothing into it. **The residue is stated, not removed:** (a) a hard kill (a power cut) between steps 2 and 3, a few milliseconds, leaves one live book of the owner's with no payload and no entry in the index, and the next run of the same file makes a second, complete book; (b) a capture of the crawl that has already looked up the hash, found nothing, and files its book after this command has claimed the hash, ends with two live books of the same bytes: its own `register` is ignored and its book is not weeded (`capture_url` is not changed by this plan). Neither damages anything or loses a file; each leaves a duplicate that the owner can weed, and a todo item records them. **Operationally, the owner loads the folder with the stop file of the crawl in place**, so that no capture of the crawl is running; (b) is not tested, because it needs a pause inside `capture_url`.
- **A file name is untrusted text.** One cleaned form, `textutil.clean(<basename without the folder>, 200)` (control, bidirectional and zero-width characters removed, white space collapsed, cut), is used for the title, for `source["file_name"]` and for every line the command prints; the raw name is stored and shown nowhere.
- The store, the identity index and the stages are used as `capture_url` uses them (`create_book`, `add_version`, `file_payload`, `merge_identity_keys`, `ident.register`, `stages.mark`); the plan changes none of them.
- This is a change to `engine/kb`, so it **voids the approval of the running crawl** the moment its files reach `main`. It is built in a separate worktree and copied to `main` in one step, after the owner is told, and should be bundled with other changes of the engine so that the owner approves once.

## Completion criteria

1. `kb capture-file <file.pdf>` files one book: kind `paper`, shelf `default`, `auto_filed` not set, the file stored as `paper.pdf` and equal byte for byte to the source, the identity key `sha256`, a `filed` event, and the stage `fetched` done; the command prints one line of JSON for it.
2. A file whose content hash the library holds (a live book) is not filed again: the status is `duplicate` and the line names the book, whatever interrupted an earlier run (a claim with no book, a book with no payload) and with two runs started together (the second is refused by the lock, and no second book exists).
3. A file that does not begin with `%PDF-`, is larger than the limit, is a link, or is not a regular file is refused with a fixed reason and files nothing; a folder argument takes the `.pdf` files directly inside it (any case of the extension), in name order, skips every other entry and says so, and a refusal of one file does not stop the others.
4. The title is the file name without `.pdf`, and the name stored and printed is the same text: one cleaned form of the base name (control, bidirectional and zero-width characters removed, at most 200 characters); the folder of the file is not stored, and the raw name is stored nowhere.
5. After `kb process`, a filed book is scanned, converted and indexed like any book (shown on a fixture PDF).
6. The tests of the area and `wb run code-work check` pass.

## Increments

### Increment A — The capture of one PDF file

**Outcome:** `capture_file.capture(store, ident, path, max_bytes=...)` files one PDF file as a book of the owner's, and refuses what it must, as criteria 1 to 4 say (the one file part).
**Dependencies:** none.
**Affected areas:** `engine/kb/capture_file.py` (new), `engine/tests/test_capture_file.py` (new).
**Steps:**
1. Read `capture_url.capture` (from the digest to the end), `_live`, `_register_from_source`, `capture_arxiv.capture`'s filing, `store.create_book`, `add_version`, `file_payload`, `merge_identity_keys`, `identity.Identity`, `stages.mark` and `textutil.clean`; write in the Result the exact order of calls for one file and how a duplicate is told (`ident.lookup("sha256", digest)` and `_live`), and what the store does with a title of 300 characters.
2. Tests first, with a temporary library and fixture files, each seen to fail for the right reason: (a) a PDF fixture is filed: kind `paper`, shelf `default`, `auto_filed` not true, `paper.pdf` equal to the source, `identity_keys["sha256"]` holds the hash, `filed` event, stage `fetched` done, the result `filed` with the book and version; (b) the same bytes under another name give `duplicate` and the id of the first book, and no second book exists; (c) a duplicate of a book that was never made (a stale entry of the index) is filed; (d) a file that begins with `%PDF` but not `%PDF-`, an empty file, and a text file named `.pdf` are refused as not a PDF, and a file that is only the header `%PDF-` is filed (only the header is checked here, and the scan and the converter say what the file is later; the test states this); (e) a file one byte over the limit is refused with no book, one at the limit is filed; (f) a symbolic link to a PDF, a link in the last component, a directory, a FIFO and a missing path are refused with no book and no hang; (g) a file that is replaced by a link between the check and the open is refused (the open uses `O_NOFOLLOW`); (h) a file name with control characters, a newline, bidirectional and zero-width marks, and one of 400 characters gives the same cleaned form (at most 200) as the title and in `source["file_name"]`, with no raw form anywhere in the book (the root file, the version source and the events are searched), and no folder name is stored anywhere; (i) an error at each point of the filing after the book is made (the claim, `add_version`, `file_payload`, the stage, the event: the store is made to raise at the nth call, for every n, and a `KeyboardInterrupt` at one of them) leaves no active book, or a book that the next run finishes with the same file, and never two live books of the same bytes; (j) an entry of the index that names a book that does not exist is taken over and the file is filed; (k) a live book with the hash whose stage `fetched` is not done is finished and is the one reported; (m) with a capture of the same bytes by `capture_url` that starts after the claim of this capture, the crawl-side call answers `held` and writes nothing into the book; with the claim made first by `capture_url`, this capture reports a duplicate and weeds its own empty book, leaving one live book (made by pausing this capture at a hook between its steps); (n) a failure after the claim, followed by two successful runs on the same file: the first run after the failure owns the key of the index, and the second reports a duplicate of it (a holder that is weeded is taken over); (l) a second run while the lock is held is refused with the fixed reason, files nothing, and the first run is not disturbed; the lock is free again after a run that raised.
3. Write the module: `lock(index_root)` (a context manager: an exclusive, non-blocking `flock` on `capture-file.lock` in the index root, refused with a fixed reason when held, always released), and `capture(store, ident, path, max_bytes=...)`: open with `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, `fstat` the descriptor for a regular file and its size, read at most `max_bytes + 1` bytes, check the first five bytes, hash; look up the hash; with no live holder make the book (the hash among its identity keys), **then claim the hash with `ident.register`** and read the holder with `ident.lookup`, and decide as the assumptions say (duplicate and weed the losing book, take over a stale entry, finish an unfinished book, or go on); file as `capture_url` does for a PDF, with `source = {"file_name": <name>, "sha256": ..., "bytes": ..., "retrieved": <time>}` and `tool = "capture-file <version>"`; `auto_filed` is not passed.
4. Deliberate single changes, each compile-checked, each restored byte for byte, each caught by a test: the `O_NOFOLLOW` flag; the header check; the size check (one byte); the order (the claim made before `create_book`); the weeding of the losing book; the take-over of a stale entry; the finish of an unfinished book; the lock; the `fstat` check for a regular file; the title cleaning.

## Risks and sensitive actions

- **Untrusted input from the filesystem, then a parser.** The command reads bytes and stores them; it never parses. A hostile PDF is read later by the scan and the converter, which run in the sandbox with limits on memory, time and file size. A security review is asked for before the commit of Increment A: the opening and the reading of the file (links, special files, races, a file that grows, a very large file), the hash and the duplicate rule, what the title and the file name can carry into the library, and that no path leaks into the stored records.
- **The approval of the crawl is voided** when the files reach `main`. Bundled with other changes of the engine, one approval covers all.
- **The owner's data.** The command reads the owner's files and does not move, change or delete them. The library gets a copy; 1 GB for this folder, against 24 GiB free and a floor of 10 GB.
- **Time and load after loading.** 61 large books will be scanned, converted, indexed and carded; a card of a long book takes many model calls on the owner's server, and the idle window makes themes for them only after the cards exist. Nothing here starts those steps by itself.

## Result

### Increment A

Built in a separate worktree (`wt-pdf`, branch `pdf-load`, from `098ab8d`), so that the approval of the running crawl was not voided while it was written and reviewed; it was copied to `main` and committed with the word of the owner (the copy voided the approval of the crawl).

**Step 1, what was read.** The order of calls for one file in `capture_file.capture`: the limit is checked; the base name is cleaned (`textutil.clean`, 200 characters, no final `.pdf`, `untitled` if nothing is left); the file is opened (`O_RDONLY|O_NOFOLLOW|O_NONBLOCK|O_NOCTTY`), `fstat` says a regular file of at most the limit, and at most limit+1 bytes are read; the header `%PDF-`; the hash; `ident.lookup("sha256", hash)` and the state of the holder (`stale`: no book, a book that cannot be read, or one that is not `active`; `unfinished`: an active `paper` of the owner's with no `url` or `arxiv` key and a stage `fetched` that is not done; `finished`: anything else); a finished holder is a `duplicate`, an unfinished one is finished with the file, a stale one leads on: `create_book` (kind `paper`, shelf `default`, `auto_filed` not set, the hash among its identity keys), `register` (no entry) or `reassign` (a stale entry), a second `lookup` (a claim made in between by another wins and this book is weeded), then `_file`: `add_version` with the source `{file_name, sha256, bytes, retrieved}` (or `set_version_source` on the current version of an unfinished book), the check that a payload filed earlier has the file's hash, `stages.reconcile`, `file_payload` of `paper.pdf` if none is filed, the `filed` event if there is none for the hash, and `stages.mark fetched done`. A duplicate is told by `ident.lookup` and the state of the book, not by `capture_url`'s `_live`, which only asks whether a book exists (a weeded book is not a holder here). The store keeps a title of at most 500 characters (`TITLE_CHARS`) after `textutil.title`, which blanks a title that spells the marker words; the cleaned name is at most 200 characters, so the cut does not apply, but a name such as `untrusted text.pdf` gets an empty title and keeps its name in the source (tested).

**What was done.** `engine/kb/capture_file.py` (new): `lock`, `clean_name`, `capture` and the helpers; `engine/tests/test_capture_file.py` (new): 38 tests.

**Departures from the plan's wording, for the owner to accept.**
1. Test (h) names a file name of 400 characters; the file system refuses more than 255 bytes, so the test uses 240 (the cut to 200 is shown).
2. The module returns `refused` with a fixed reason for a file it will not take, and raises `KbError` only for a bad limit, a lock that is held, or a store that fails; the command of Increment B turns each into a line for that file.
3. "Finish an unfinished book" is limited to books this command could have made: kind `paper`, not `auto_filed`, no `url` or `arxiv` key. A book of any other kind that holds the hash is a duplicate and is never written into (from the security review).
4. A payload filed by an earlier try is checked against the file's hash before `reconcile` adopts it, and a different payload is a refusal (from the security review).
5. The plan's break "the order (the claim made before `create_book`)" is run as the break that moves `create_book` after the claim.
6. A test with the real `capture_url` (the crawl-side half of test (m)) was not written: it needs the whole web-client policy. That a crawl capture answers `held` for a live book that is not the crawl's rests on reading `capture_url.capture` and on the tests of this module at the claim.
